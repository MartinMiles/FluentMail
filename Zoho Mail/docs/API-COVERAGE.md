# API coverage and implementation boundaries

## v1.5: embedded images and conversations

[List emails](https://www.zoho.com/mail/help/api/get-emails-list.html) supports threadedMails, threadCount and threadId. threadedMails is a filter for conversation mail, not a grouping mode; omit it for normal lists so standalone messages remain visible. Conversation membership uses the same endpoint with threadId, includesent=true and includearchive=true, omitting folderId; 40 summaries/page. Grouping never guesses from subjects and always respects the authorization/mailbox boundary. Bodies are fetched only when expanded. Existing message actions remain message-scoped.

[Attachment info](https://www.zoho.com/mail/help/api/get-attach-info.html) with includeInline=true exposes inline[].cid/name/size. [Download inline image](https://www.zoho.com/mail/help/api/inline-image-download.html) is GET /api/accounts/{a}/folders/{f}/messages/{m}/inline?contentId=...&fileName=... under existing messages.READ scope. Match only server-confirmed parts; never send OAuth to a URL supplied by HTML. Embedded raster bytes are validated and passed as memory-only data URIs to the isolated reader. Twenty parts/20 MB combined limit; remote images stay blocked. No subscription, IMAP or scope expansion.

## v1.4: owner-approved SMTP inline sending

Messages with local pasted images use Zoho SMTP with standard CID/MIME inline parts. This is a supported mail protocol, not a new invented Mail API operation. Other sends, receiving and mailbox actions retain the API implementation and existing scopes. SMTP credentials are separate, encrypted and scoped to profile/account. There are no API image uploads/posts on this route. Certificate checks are mandatory, there is no retry/pooling, and live eligibility needs the actual account credential. SMTP Sent copies are normally server-managed; inline messages send now and drafts stay local. See [the resolution](INLINE-IMAGES.md) and [Zoho SMTP configuration](https://www.zoho.com/mail/help/zoho-smtp.html). Earlier API-only scope statements below are historical.

## v1.3 correction — verified behavior

Recipient history seeds one page of Sent through the existing list API and then uses mailbox-scoped encrypted local data; no contact API scope is added. List requests retain folderId but no longer explicitly exclude Sent. Send now and the countdown are local. Del moves to the source mailbox's Trash through the existing move API.

Live tests showed that normally HTML-escaped preview URLs, direct data URI HTML and filename/path CID references did not produce matching inline parts. A later vetted literal-query-separator workaround produced working inline CID images, verified in Gmail, but also ordinary duplicate file attachments. Removing descriptors or supplying an empty list stopped conversion. Production image send/cloud-save remains blocked before upload because the no-duplicate requirement is unresolved; local drafts retain images. The inline-upload primitive keeps regional host/path validation; its internal image-URL account ID need not equal the public API account ID (the official example differs). See [the investigation](INLINE-IMAGES.md). Historical v1.2 claims below are superseded here. No guessed association fields/private endpoints are shipped.

## v1.2 update

Local clipboard images now upload through the same documented RAW attachment endpoint with `isInline=true`; the returned `url` is validated for region/account and substituted into the matching HTML img source. No CID or new API scope is invented. Regular clipboard files use the normal attachment path. Live external inline-image rendering remains unverified. The five-second Send delay is entirely local and starts no upload/API send until it expires.

## v1.1 update — 2026-10-28

The same mailbox scopes and documented endpoints now support automatic Inbox polling and WYSIWYG HTML composition. New mail is detected from paced `messages/view` requests; no webhook relay or private endpoint was added. Healthy connected sessions use the documented refresh-token grant once before expiry; failures still pause without retries. Send/reply/cloud-draft payloads use `mailFormat: html` with main-process sanitization; v1.0 plaintext payloads remain valid.

The original scope decisions below are historical where they mention plain-text-only composition, manual refresh, or no background checks. v1.1 preserves rich signatures/quotes and safe text formatting, but still excludes inline-image uploading, arbitrary remote content, administration, permanent deletion, and a hosted push service. See `PLAN-1.1.md` for source links and reasons. The owner reports v1.0 connection and external attachment delivery succeeded; v1.1 operations remain offline-tested by the assistant.

Research checked against official Zoho documentation on 2026-10-27. API requests are constructed only in `desktop/zoho.ts` and `desktop/transport.ts`. The renderer sends validated operations, never arbitrary remote URLs. Numeric IDs remain strings; JSON-bigint prevents precision loss from unquoted server IDs.

## API families reviewed, deliberately outside this mail client

The [complete API index](https://www.zoho.com/mail/help/api/) also contains organization, domain, group, user, mail-policy, logs, anti-spam administration, tasks, notes, bookmarks and thread-wide mutation APIs. They are documented capabilities, not promises that every free organization can use every endpoint.

- Organization/domain/user/group administration remains in Zoho Admin. No admin scopes are requested. DNS, subscriptions, catch-all and user creation are outside this client.
- Tasks, notes, bookmarks, projects and group collaboration would turn a small mail client into another suite. No placeholder buttons are presented for them.
- Mail account configuration changes, forwarding, vacation replies, security policy and identity changes are not exposed. Some are plan-restricted, and they are not needed to replace the mail view.
- Whole-thread actions are not substituted for selected-message actions. There is no separate conversation-folding UI yet; each message can be read and replied to with its original reference.
- Permanent deletion, folder emptying, folder deletion, label deletion and remote signature editing are not exposed in this release.
- No invented contact/calendar synchronization API, IMAP/SMTP bridge, cookie scraping, mobile-app impersonation, or undocumented private API.
- Complex HTML composition, inline images, automatic forwarding of original attachments, offline mailbox caching, and push notifications are not implemented. These are client scope decisions, not blanket claims that Zoho cannot support them.

## Authentication, limits and response handling

[Self Client](https://www.zoho.com/developer/oauth/self-client/overview.html) authorization codes are exchanged at the selected Accounts host's `/oauth/v2/token`. A refresh token is used only on explicit Connect. [OAuth guide](https://www.zoho.com/mail/help/api/using-oauth-2.html).

The documented Mail API policy is [30 requests per minute](https://www.zoho.com/mail/help/adminconsole/rates-and-limits.html). The client serializes all profiles through one pacer with 2.6 seconds between starts (under 24/minute). Search does not fire on every keystroke. There are no retries or periodic collectors. Failed authentication, redirects, malformed bodies, rejection, rate limits and uncertain network results pause the affected profile. Queue entries recheck connection state before execution.

Use only account IDs returned by the matching authorization. Provider error payloads are not echoed to the UI or logs because they may contain confidential data. APIs and free-account entitlement remain unverified against live production accounts; fixture tests verify request construction and error behavior.
